# AgileConfig 用户与权限管理实践

本文整理 AgileConfig **多用户与权限**的设计与用法，主要依据 [AgileConfig 轻量级配置中心 1.3.0 发布，支持多用户权限控制](https://cloud.tencent.com/developer/article/1836666)（腾讯云开发者社区，2021-06）及作者公开说明。若你使用的服务端版本较新，界面字段可能略有演进，但**角色分层 + 应用管理员 + 按应用授权**的思路仍然适用。

---

## 设计理念与背景

AgileConfig 当初是设计给我自己用的一个工具，所以只设置了一道管理员密码，没有用户的概念。但是很多同学在使用过后都提出了需要多用户支持的建议。整个团队或者整个公司都使用同一个密码来管理非常的不方便。

今天 **AgileConfig 1.3.0** 版本终于支持了多用户，以及简单的权限管理。用户跟权限的设计，在我们开发管理系统的时候经常涉及，最常用的就是 **RBAC**（基于角色的权限控制）。但是基于 AgileConfig **简单**的理念，稍微简化了一点权限控制的功能设计，尽量的降低学习成本。

---

## 权限设计

AgileConfig 的权限设计分为 **3 个固定的角色**：

### 超级管理员

超级管理员具有**一切的控制权限**，可以随意添加、修改、删除用户、应用、配置等任何信息。

### 管理员

普通管理员可以**新建应用**；可以删除、修改**属于他的应用**（应用的管理员属性为当前用户），以及该应用的配置项。管理员可以给任何用户**授权**所属应用配置项的管理权限。管理员可以添加、修改、删除角色为**操作员**的用户。

### 操作员

操作员对应用**没有任何控制权限**，只能**编辑**或者**发布、下线**经过管理员授权的应用的配置项。

**实现侧说明**：操作员对应角色枚举常为 `NormalUser`，与 UI 文案「操作员」一致。

#### 角色能力一览（速查）

| 角色 | 能力概要 |
|------|-----------|
| **超级管理员** | 全局最高权限：用户、应用、配置等均可维护。 |
| **管理员** | 新建应用；维护「自己是应用管理员」的应用及其配置；授权；维护操作员用户。 |
| **操作员** | 无应用级控制；仅能在授权范围内编辑配置并做发布/下线。 |

## 用户管理

1.3.0 版本新增了多用户支持，那么**用户管理**是必须的功能。以下说明如何在控制台维护用户（需具备相应权限的账号登录后操作）。

### 操作要点

1. 使用**管理员级别**（超级管理员或管理员）账号登录管理控制台。
2. 进入 **「用户」** → **「添加」**。
3. 填写 **用户名、密码、团队** 等基本信息，并选择 **角色**。
4. 保存成功后，新用户即可用该账号登录。

## 应用授权：两层含义

### 1. 应用管理员（应用归属）

在**新建或编辑应用**时，指定 **应用的管理员用户**。该用户对该应用拥有**完全控制**（应用与配置项的维护边界以当前版本 UI 为准）。

### 2. 对其他用户的细粒度授权

对需要协作、但不应拥有应用级管理权的账号，使用 **「授权」** 入口，通常包含两类能力（原文表述）：

- **配置修改权**：配置项的改、删、查（在授权范围内）。
- **配置上下线权**：配置项的**上线、下线**。

管理员按人、按应用授予上述权限后，操作员即可在授权范围内工作。

## 从 1.2 升级到 1.3 时的数据库变更（历史说明）

1.3 引入多用户后表结构有增量。若从 **1.2 升级到 1.3** 未执行迁移，可能出现启动或运行错误。原文以 **MySQL** 为例，主要包括：

- `agc_app` 表新增字段 **`app_admin`**（`varchar(36)`）。
- 新建表 **`agc_user`**、**`agc_user_app_auth`**、**`agc_user_role`**（用户、用户对应用的权限、用户与固定角色的绑定）。

完成表结构变更并重启服务后，按原文描述会**提示重置超级管理员密码**，之后按新用户体系使用即可。

> **建议**：当前若已远高于 1.3 版本，请以**官方发布说明 / 自带迁移脚本**为准；本节仅保留对旧文「升级路径」的摘要，避免与新版自动化迁移重复劳动。

## 落地建议（实践向）

- **超级管理员账号**：严格控制人数，专用于用户与全局治理。
- **按应用设管理员**：业务线或系统负责人担任「应用管理员」，负责本应用与协作者授权。
- **操作员**：适合只改配置、不碰应用生命周期的开发/运维；通过「授权」限定可编辑与可上下线的范围。
- **审计与责任**：结合团队规范约定「谁授权、谁审批」，与 AgileConfig 的权限模型对齐。
